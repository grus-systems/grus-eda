# e6-drt-tracks — Overview

E6 ticket 2: the on-grid substrate the maze router needs — per-layer,
per-axis track coordinates and candidate access points for every
signal-net member pin. Ticket 1 (`e6-drt-ref`) landed the delegation
reference; this ticket is the first implementation slice.

## Ground truth discovered while planning

- **DEF `TRACKS` is already parsed.** `def.rs` produces
  `DesignDb::tracks: Vec<TrackGrid>` (`is_vertical_tracks`,
  `start_dbu`, `num_tracks`, `step_dbu`, `layers`). DEF values are
  already DBU. `gcd.placed.def` and `picorv32.placed.def` each carry
  12 `TRACKS` statements: X and Y for `li1`, `met1`–`met5`.
- **The sky130 techlef carries zero `TRACKS` statements** (verified by
  grepping `sky130_fd_sc_hd__nom.tlef`). The LEF `TRACKS` parse this
  ticket adds is grammar support exercised by synthetic fixtures; the
  real-design grids come from the DEF merge. The doc must say so —
  claiming "sky130 LEF TRACKS parsed into lists" when the lists are
  empty is the vacuous-coverage failure of AGENTS §7.4.
- **`RoutingLayer::dir` already holds the LEF `DIRECTION`** (parsed in
  `parse_layer`). No new preferred-direction source needed.
- **`net_names` is exactly the `NETS` section** (signal nets);
  `SPECIALNETS` go to `pdn_nets`. `db.net_pins(net)` yields member
  `PinId`s in DEF connection order and includes io `PIN` conns —
  iterating it covers instance pins and `BTERM` ports alike.
- **Pin shape sources already exist:**
  - instance pin → `db.pin_macro_pins[p]` → `MacroPin.rects`
    (`Vec<(LayerId, RectDbu)>`, macro coords) →
    `DesignDb::orient_rect` + cell translate (the same transform
    `drc::geom::assemble` source 4 applies); gate on
    `cell_status ∈ {Placed, Fixed, Cover}`.
  - io pin → `db.pin_io_rects[p]` (`Vec<(LayerId, RectDbu)>`, absolute).
- `picorv32.placed.def` is gitignored — generated by
  `tests/designs/picorv32/generate_ref.sh`; tests panic loudly when it
  is absent (existing convention).

## Decisions (detail in the sibling docs)

1. **Two-source track model.** `RoutingLayer` gains
   `tracks_x`/`tracks_y: Vec<i32>` — expanded, sorted, deduped DBU
   coordinates from **LEF** `TRACKS` records (empty on sky130). The
   per-design effective grid `drt::tracks::layer_tracks` merges those
   with expansions of `DesignDb::tracks`. LEF and DEF provenance stay
   distinguishable (LEF lives on `RoutingLayer`, DEF on `DesignDb`).
2. **Deferred LEF expansion.** `TRACKS` may precede `UNITS` and the
   `LAYER` it names; raw µm records accumulate on `TechDb` (transient,
   `serde(skip)`) and expand at the end of `parse_lef_bytes`, mirroring
   the `cut_res_above` → `via_res_ohm_above` pattern.
3. **AP midpoint model** (ours, not TritonRoute's): a vertical track
   `x = t` with `t ∈ [xl, xh]` yields one access point `(t, (yl+yh)/2)`;
   a horizontal track `y = t` with `t ∈ [yl, yh]` yields `((xl+xh)/2, t)`.
   Boundary inclusive. One point per track line, per rect.
4. **Named findings, not silent zeros.** The report carries
   `off_track` (had shapes, zero APs), `no_shapes` (no candidate rects:
   unplaced cell or unmapped macro pin), and `drt::tracks::track_gaps`
   (routing layer whose preferred axis has no tracks). All three must
   be empty on gcd/picorv32; any entry is a named finding.
5. **Census runs on `*.placed.def`** — the router's real input and the
   DRT reference's `input_def`.

## Non-goals (per spec)

Maze routing, vias, DEF route emission, track assignment, DRC-aware AP
pruning. The claim boundary for what access points *mean* is written
into `docs/e6-drt.md` (see `docs.md`).
