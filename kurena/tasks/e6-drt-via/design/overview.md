# e6-drt-via — Overview

E6 ticket 4: the via model for the guide-bounded track graph. Two
halves: (a) the **candidate table** — which LEF `VIA` / DEF `VIAS`
defs may connect each adjacent routing-layer pair, with each def's
rects expanded at the origin for later DRC-aware costing, plus the
named default pick per pair; (b) **via edges** in `drt::graph` —
layer-transition edges between nodes at a shared track crossing.
Depends on `e6-drt-graph` (landed).

## Ground truth discovered while planning

- **The LEF `VIA` model is already fully parsed.** `TechDb::via_defs`
  carries every `VIA` block with `lower`/`upper` (min/max routing
  `LayerId`), `cut` (first cut-group name), `cut_count`, and every
  `RECT` in group order (`lef.rs:740-856`). Matching a pair is
  `vd.lower.0 == k && vd.upper.0 == k+1`. On the sky130 techlef there
  are exactly **25 defs** — five cut layers (mcon, via, via2, via3,
  via4) × five variants (`PR`, `PR_R`, `PR_M`, `PR_MR`, `PR_C`), all
  adjacent single-cut stacks — so every pair (li1–met1 … met4–met5)
  gets ≥5 LEF candidates.
- **DEF `VIAS` defs are parse-local and dropped.** `DefViaMap`
  (`readers/def.rs:566`) is built inside `parse_def` and discarded —
  only `PdnVia` *instances* in SPECIALNETS/NETS wires retain resolved
  triples. Both placed DEFs declare a `VIAS 4` section (`via2_3_*`,
  `via3_4_*`, `via4_5_*`, `via5_6_*` — generated `+ VIARULE` vias for
  pairs met1–met2 … met4–met5; nothing for li1–met1). To enumerate
  them per scope item 1, `DesignDb` must retain resolved records — a
  small additive change (`design_db.rs` + `readers/def.rs`), added to
  the ticket's `## Files`.
- **`drc::geom::expand_via` is the reuse path the goal names.** It
  expands `ViaGeom::Lef` (rects verbatim) and `ViaGeom::Generated`
  (OpenDB enclosure/cut-array arithmetic) to absolute
  `Vec<(DrcLayer, RectDbu)>`, golden-verified against a committed DEF
  record. Call it on a synthetic `PdnVia` at (0,0) to get via-local
  candidate rects.
- **Measured via geometry** (techlef rects): within each family the
  four non-`_C` variants tie on total area; `_C` is strictly larger
  (e.g. L1M1 0.1419 vs 0.1245 µm²). What differs is metal
  *orientation* vs preferred direction: `PR` extends each metal along
  its layer's preferred direction, `PR_R` neither, `PR_M` lower-only,
  `PR_MR` upper-only. Two degeneracies: `L1M1_PR` and `L1M1_PR_MR`
  are **rect-for-rect identical**, and all five `M4M5` variants are
  identical.
- **The spec's via-edge rule produces zero met2–met3 edges — measured.**
  Shared `(x,y)` crossings between adjacent grids (pre-coverage,
  computed from the committed `TRACKS`):

  | pair | gcd shared crossings | picorv32 shared crossings |
  |---|---|---|
  | li1–met1 | 3,624 | 89,776 |
  | met1–met2 | 156 | 3,906 |
  | **met2–met3** | **0** | **0** |
  | met3–met4 | 42 | 961 |
  | met4–met5 | 1 | 36 |

  met2 coords are `230+460k ≡ 10 (mod 20)`; met3 `340+680k ≡ 0
  (mod 20)` — the grids never coincide on either axis, on either
  design.
- **The reference places vias at preferred-track anchors, not
  two-layer crossings — measured on `gcd.routed.def`:**

  | via | total | at strict shared crossing | at preferred anchor* |
  |---|---|---|---|
  | L1M1_PR_MR | 884 | 50 | 769 (115 off — pin-access relaxations) |
  | M1M2_PR | 881 | 3 | 881 |
  | M1M2_PR_MR | 2 | 0 | 2 |
  | M2M3_PR | 28 | 0 | 28 |
  | M3M4_PR | 2 | 0 | 2 |

  \* x on the vertical layer's `tracks_x`, y on the horizontal
  layer's `tracks_y`. TritonRoute's via sits at e.g.
  `(met2_x, met3_y)` — a node on **neither** layer under our
  same-layer-crossing node model. So the strict rule is implementable
  as specced but structurally cannot represent the reference's
  dominant via positions: met2–met3 is unreachable in the graph
  (28 vias on gcd, 1,784 on picorv32 in the routed DEFs). This is a
  **named model gap for the maze ticket**, not something this ticket
  papers over — the node model itself would have to change (e.g.
  union non-preferred grid, TritonRoute-style), which is outside
  `e6-drt-graph`'s landed semantics.
- **Reference picks** (`<d>.drt.reference.json` `variants.baseline
  .vias_per_cut_layer`, both designs): mcon→`L1M1_PR_MR`,
  via→`M1M2_PR`, via2→`M2M3_PR`, via3→`M3M4_PR`, via4→unobserved
  (zero M4M5 instances in either routed DEF). DRT-0167 "List of
  default vias" prints in the log but the names themselves are not
  captured by the committed parser — the routed-DEF census is the
  joinable evidence.
- `picorv32.placed.def` is gitignored (generated by
  `tests/designs/picorv32/generate_ref.sh`; present on the planning
  machine). Tests panic loudly when absent — existing convention.

## Decisions (detail in the sibling docs)

1. **Implement the spec's strict rule**: a via edge connects a node
   on `l` to the node on `l+1` at the same `(x,y)` — which exists iff
   `(x,y)` is a crossing on `l+1` (any node is a crossing on its own
   layer by construction) and is guide-covered. met2–met3 yields 0
   edges on both designs — pinned in the gate and named a **tech gap
   in the edge domain**, with the preferred-anchor measurement and
   the deferred node-model fix recorded in `docs/e6-drt.md` +
   `docs/results.md` (`via-edges.md`).
2. **Edge emission is purely geometric** (the spec's rule): shared
   crossing + guide coverage on both layers — no dependence on the
   candidate table, so `build_route_graphs` keeps its 4-arg signature
   and `graph.rs` never imports `via.rs`. A pair with zero candidates
   is a `ViaGap` (named), and any edges the geometry still yields are
   the data explaining the gap; the maze router joins table + graph
   to price transitions, so no phantom routability (`via-edges.md`).
3. **Retain resolved DEF `VIAS` records** in `DesignDb::def_vias`
   (generated + `+ VIA` aliases resolved to `ViaGeom::Lef`; `+ RECT`/
   `+ POLYGON` inline records store nothing — lazy-error semantics
   unchanged). Candidates are enumerated per name — a `+ VIA` alias
   is its own candidate (same def, distinct DEF name).
4. **Default-via policy** = argmin(`nonpref_metal`, `area_dbu2`,
   declaration order): prefer metals aligned to preferred direction,
   then smallest total painted area, then file order. Yields
   `{L1M1_PR, M1M2_PR, M2M3_PR, M3M4_PR, M4M5_PR}` — matches the
   reference majority on via/via2/via3; mcon diverges in **name
   only** (`L1M1_PR` ≡ `L1M1_PR_MR` rect-for-rect — asserted in the
   gate, documented); via4 unobserved → policy pick `M4M5_PR`.
5. **`ViaEdge { lower, upper }` node-id pairs in
   `NetGraph::via_edges`** — separate from in-plane `edges` (the
   maze router prices them differently); per-pair totals on
   `RouteGraphs::via_edges_per_pair`.
