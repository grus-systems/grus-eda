# Project Review (2026-11-11)

Reviewer: an AI reviewer, at commit `434afc4` (`dev`, version 0.1.19, about 12,500 lines of Rust).

Two questions were asked: what should be fixed, and what it would take to make this a
replacement for the existing open-source EDA flow rather than a preflight estimator.

## 0. What was run

Everything below marked "measured" was run for this review on an Apple M1 Pro, release build.

| Command | Result |
|---|---|
| `cargo build --release` | ok |
| `cargo test --release` | 51 passed, 0 failed, 1 ignored (picorv32 placement RC), 16.4 s |
| `cargo clippy --all-targets` | 1 warning (`needless_range_loop`) |
| `grus-eda congestion` on `picorv32.placed.def` | 65 ms, total overflow 0 |
| `grus-eda place` on `picorv32.floorplan.def` (default density 0.60) | 2.6 s; see finding F1 |
| `grus-eda sta` on picorv32, zero wire | 5.8 ms |
| `grus-eda sta` on picorv32, SPEF | 16.5 s |

Not run: the reference tools (no container was started), so no golden file was regenerated and
our picorv32 placement was not checked by OpenROAD's `check_placement`. The code was read in full
for `sta/`, `main.rs`, `nesterov.rs` and the DEF writer, and in part for the other modules.

## 1. Summary

The project is in better shape than its size suggests, and the reason is the verification
discipline, not the algorithms: golden files come from committed scripts, failures stay in
`docs/results.md` with a root cause, tests are broken on purpose to prove they can fail, and
tolerances are loosened only with a named cause. That is rare and should be kept at any cost.

The weak point is the distance between what the documents claim and what has been shown:

- **Evidence is thin.** E1 and E2 are "PASS" on one design of 233 cells. The README goal is
  100k cells. The only larger design (picorv32, 10k cells) is used by E3 only, and on it E2 does
  not converge (F1) and E1 has nothing to measure (F2).
- **The README describes a design that the code does not have yet**: parallel levelized STA,
  CSR graphs, rayon, SIMD. None of these exist (F8). That is fine for "agreement before speed",
  but the documents should say so.
- **The "seconds" goal is already missed in one place**: STA with parasitics takes 16.5 s on
  10k cells (known, task E3.6), and the legalizer scales worse than linearly (F5).

## 2. Findings

Ordered by how much they matter. "Fix" is what I would do; none of it has been done.

### F1. `place` reports convergence when it hit the iteration limit (measured)

On picorv32, `grus-eda place` prints

```
Global placement: converged in 299 iters, final_overflow=0.2360, ...
```

`max_iters` is 300 and the stop criterion is overflow <= 0.10, so the placer did **not**
converge: it ran out of iterations at overflow 0.236 and the legalizer absorbed the rest
(max displacement 21.75 um). `NesterovResult` has no "converged" field and
`crates/grus-eda/src/main.rs` prints "converged" unconditionally. `iterations` is also the last
loop index, not the count.

The final HPWL is 207,079 um against 202,261 um for OpenROAD's `picorv32.placed.def`
(+2.4%), but the two runs used different target densities (0.60 here, 0.55 there), and legality
was not checked by OpenROAD, so this is not a comparison yet.

Fix: return `converged: bool`, print the truth, exit non-zero (or warn loudly) when the limit is
hit. Then add picorv32 as an E2 test (same density as the reference, `check_placement` in
`generate_ref.sh`) and record the result in `docs/results.md`, pass or fail. The E2 status in
`docs/results.md` should read "PASS on gcd only; picorv32 does not converge" until then.

### F2. The E1 criterion cannot fail in an informative way

"Overflow ranks the test variants in the same order" is checked on four utilisation variants of
gcd. Three things make this weak:

- Absolute overflow is off by up to 5.7x (alpha 0.80, util 25%: OpenROAD 154, ours 27). Rank
  order of four points hides that.
- The pass depends on a suboptimal Steiner tree. With the exact tree the ranking test breaks
  (a tie, `docs/results.md` E3.4), so E1 keeps the greedy one. A result that only holds for one
  particular heuristic is fitted to its test.
- picorv32 has zero overflow in both tools' settings, so the larger design adds no evidence.

Fix: compare the congestion **map**, not the total. Dump per-GCell usage from OpenROAD
(`dbGCellGrid`, already used in `generate_ref.sh`) and report the rank correlation (Spearman)
between the two maps and the overlap of the top 5% most congested GCells. Use designs that are
actually congested (`aes`, `ibex`, `jpeg` from OpenROAD-flow-scripts at high utilisation). The
rank-order test can stay as a smoke test.

### F3. STA silently drops what it does not model

`sta/analysis.rs` handles rising-edge flip-flops, one ideal clock, setup and hold. Everything
else is skipped without a message, which is the dangerous direction for a timing tool:

- `TimingType::FallingEdge`, `SetupFalling`, `HoldFalling`, `RecoveryRising`, `RemovalRising`
  fall into `_ => {}` in `build_graph`. A falling-edge register simply has no endpoint.
- A register check with only one of setup/hold, or an endpoint that no path reaches, is dropped
  in `collect_endpoints` (`continue`).
- The clock is ideal: every `CLK` pin gets arrival 0 and slew 0, even when the DEF holds a
  clock tree. On a post-CTS design the result is wrong with no warning.
- More than one `create_clock` overwrites the first. `-no_clocks`, `-min`/`-max`, `-add_delay`
  and other flags are parsed away as unknown flags.

Latches are the one case that does warn. Fix: do the same for the others. Count what was
skipped (unsupported arc types, unconstrained endpoints, extra clocks) and print the counts in
the summary line; fail on a second clock and on flags that change meaning. Compare the endpoint
count against OpenSTA's in the tests (it is 53 and 1,798 today only because the test designs
are simple).

### F4. The DMP driver model is fitted on the design it is tested on

`RD_SCALE = 4.5` was chosen by scanning mismatch counts on picorv32 SPEF, and the picorv32 SPEF
test then passes with loosened tolerances (slack 40 ps, slew 10%). With two designs there is no
holdout, so the 0.4% WNS agreement is partly a fit. This is known (task E3.5); two additions:

- Add a third design that takes no part in any fit before changing the model again.
- The doc comment above `RD_SCALE` describes `ln(0.8 / 0.2)`, which is 1.386, not 4.5. It
  reads like a derivation and is not one.

### F5. Speed: one known problem, one new one (measured)

- STA with parasitics: 16.5 s on picorv32, 5.8 ms without. Every arc evaluation calls
  `solve_dmp` twice (late and early slew); each call is 24 bisection steps, each step fits a
  ramp (40 x 2 x 40 evaluations of an exponential) and integrates 200 implicit steps. The ramp
  response of a single RC and of the two-pole pi load both have closed forms. Task E3.6 covers
  this; I would move it ahead of E3.4 because a 16 s test suite slows every other task.
- Legalization: 6 ms at 233 movable cells, 1,878 ms at 6,709. That is about `n^1.7`. If it
  holds (an extrapolation, not a measurement) 100k cells take minutes, and the README goal is
  seconds. Profile `legalize.rs` on picorv32 before adding features to it.

### F6. Readers accept malformed input

The repository rule is "handle errors at system boundaries". The DEF reader does the opposite:
numbers are read with `.parse().unwrap_or(0)`, unknown keywords fall into `_ => {}`, a `ROW`
with too few words becomes a row at (0, 0) with zero sites. A truncated or unusual DEF yields a
plausible, wrong database. The LEF and SPEF readers should be checked for the same pattern.

Fix: return errors with line numbers for anything the grammar requires; keep an explicit
allow-list of sections that are skipped on purpose. Add a fuzz target per reader
(`cargo fuzz`): the property is "returns `Ok` or `Err`, never panics, never loops".

### F7. The CLI advertises options that do not work

- `sta` declares `--json`, `--verilog`, `--clock-pin` and `--period-ns`; all four are ignored,
  and the command fails without `--tlef --lef --def --sdc`. `docs/architecture.md` Section 5
  documents the ignored forms.
- `--parasitics` is a free string matched against three literals; use a `clap` value enum.
- `congestion --gcell-tracks` treats the value 15 as "not given".
- `--layer-adjust` builds a vector of exactly six layers with `li1` fixed at 0.

Fix: delete the options that are not implemented, or implement them. STA from a netlist with no
DEF (zero wire) is a natural first use and is cheap to add.

### F8. Documents and code have drifted (AGENTS.md Section 7, rule 8)

| Document says | Code has |
|---|---|
| README goal 3: CSR graphs, no allocation per object, levelized so each level is one parallel pass | `Vec<Vec<u32>>` adjacency, `BTreeMap` of checks, a Kahn order with no levels, a `Vec` allocated per net per visit |
| README goals 2 and 5: rayon, NEON | `rayon` is an optional dependency that no code uses; no SIMD |
| `architecture.md` 3.1: `sta/graph.rs`, `sta/propagate.rs` | `sta/analysis.rs`, `dmp.rs`, `sdc.rs` |
| `architecture.md` 3.2: version 0.1.0; `realfft` approved | 0.1.19; `realfft` declared, not used by any crate |
| `architecture.md` 2 and E2 title: "greedy legalizer" | Abacus plus four refinement rounds |
| AGENTS.md Section 6 "First Steps (E0)" | E0 to E3 exist |

Fix: mark the README goals as "target" versus "today", regenerate the layout section from the
tree, drop AGENTS.md Section 6. A short `docs/status.md` (one table: stage, designs covered,
tolerance, known gaps) would replace most of the drift-prone prose.

### F9. Tests depend on the machine

- Every integration test needs the PDK under `~/.ciel` (or `PDK_ROOT`) and, for picorv32, files
  that only a container run produces. There is no CI, so nothing proves the suite passes
  anywhere but on this laptop.
- The PDK path lookup is copied into about 14 test modules, with three slightly different
  fallbacks (`"/root"`, `"."`, `unwrap()`).
- `test_sky130_liberty_integration` asserts a 10 ms wall-clock bound and is known to be flaky.
- The Liberty cache is written next to the `.lib`, that is, into the PDK installation.

Fix: one `test_support` module for paths; move wall-clock assertions out of `cargo test` into a
benchmark; write the cache under a cache directory (`$XDG_CACHE_HOME` or `target/`), never next
to the source. For CI, the org's self-hosted Mac mini runner with the PDK installed is enough;
the three sky130 files could also be fetched by `ciel` in a setup step.

### F10. Smaller items

- `lib.rs` re-exports every module with `pub use module::*`, and lexers are `pub`. There is no
  deliberate public API; fine today, a problem the day a second crate depends on `grus-core`.
- `write_def` patches the `COMPONENTS` section of the input text by string search. It cannot
  write a design that did not come from a DEF, and `find("COMPONENTS ")` trusts the layout.
- `tns` in `collect_endpoints` sums in `f32`; `architecture.md` asks for `f64` reductions.
- `cell_pin_for_lib_pin` is a linear search per arc; negligible on sky130 cells, quadratic on
  macros with many pins.
- sky130 assumptions are spread around (DBU fallback 1000, one site, six layers). Collect them
  before a second PDK is tried.

## 3. On task E3.4 (OpenROAD's Steiner tree)

Two remarks that may save time:

1. **Check the licence premise.** AGENTS.md says OpenROAD and OpenSTA source is GPL and must not
   be read. To my knowledge OpenSTA is GPL-3, but OpenROAD itself (including its Steiner-tree
   and parasitic-estimation modules) is BSD-3-Clause, with OpenSTA vendored as a separate
   component. I did not verify this here. If it holds, the tree-building rule can be read
   instead of reverse-engineered, which is the whole of E3.4. Confirm with the licence files of
   the exact version in the LibreLane image before acting on it.
2. **Ask what the target should be.** `estimate_parasitics -placement` is itself an estimate.
   Matching its tree makes us agree with an estimator. What a user needs is agreement with
   **routed** parasitics. A routed SPEF (already listed as "not scheduled") would let both
   estimates be scored against the truth; if the exact Steiner tree is as close to routed
   timing as OpenROAD's tree, E3.4 can be closed as "different, not worse".

## 4. What it would take to replace the existing tools

### 4.1 The gap

Today this is an estimator for three questions on one PDK. A replacement for the open flow
(Yosys, OpenROAD, OpenSTA, Magic, KLayout) needs, in rough order of size:

| Area | Have | Missing |
|---|---|---|
| Database | read-only SoA, DEF in, `COMPONENTS` out | incremental edits (resize, buffer, move), undo, hierarchy, a native on-disk format |
| STA | NLDM, one ideal clock, setup/hold, Elmore + fitted DMP | propagated clocks, multiple clocks and clock groups, exceptions (false/multicycle path), latches, recovery/removal, min pulse width, max slew/cap checks, CPPR, OCV derates, multi-corner, path reports, **incremental update**, SDF, CCS |
| Placement | ePlace global, Abacus | timing-driven and routability-driven modes, macros and mixed-size, fixed blockages, density screens, detailed placement worth the name |
| Optimisation | nothing | gate sizing, buffering, hold fixing (OpenROAD `repair_design` / `repair_timing`) |
| Clock | nothing | clock tree synthesis |
| Floorplan, PDN, I/O | nothing | all of it |
| Routing | 2D congestion estimate | 3D global routing with layer assignment and guides, **detailed routing**, antenna repair |
| Extraction | Steiner estimate | rule-based or field-solver-calibrated RC extraction |
| Physical verification | nothing | DRC, LVS, fill, GDS/OASIS stream-out |
| Logic synthesis | nothing | (Yosys/ABC) |

Detailed routing with design-rule correctness and physical verification are each larger than
everything in this repository by one to two orders of magnitude, and they are where advanced
PDK rules live. OpenROAD is hundreds of thousands of lines after years of funded work.
A plan that says "replace everything" is not a plan.

### 4.2 The verification method has to change

"A stage is done when its numbers agree with the reference tool" is the right rule for an
estimator and the wrong one for a replacement: it makes the reference tool the ceiling, and it
forces work on reproducing the reference's quirks (E3.4 is exactly this). A replacement is
judged on results:

- **Legality** is still checked by the reference tools (`check_placement`, DRC, LVS).
- **Quality** is measured after the *rest* of the flow has run: place with ours, then CTS,
  route and sign-off timing with OpenROAD and OpenSTA, and compare WNS, TNS, wirelength, DRC
  count and runtime with the all-OpenROAD run on the same design.
- **STA is the exception**: a timing engine must keep agreeing with a sign-off reference,
  because its output is a claim about silicon, not a design choice.

So: keep the current rule for STA and for readers; switch placement and routing to
end-to-end QoR on a fixed benchmark set (the OpenROAD-flow-scripts sky130hd designs: `gcd`,
`aes`, `ibex`, `jpeg`, `riscv32i`, plus `picorv32`), tracked in one table per commit.

### 4.3 A staged path, each stage useful on its own

Replace from the inside out. Every stage below ships something a user can use with the
remainder of the flow still in OpenROAD, and each has a gate that can fail.

1. **Make the estimator trustworthy at its stated scale** (this is Section 2).
   Gate: all four stages pass on at least five designs up to 100k cells, in CI, in seconds.
2. **A real timing engine.** Propagated and multiple clocks, exceptions, both edges, latches,
   recovery/removal, multi-corner, path reports, and above all incremental update after a
   netlist or placement change. Everything in stages 3 to 5 calls it in a loop.
   Gate: endpoint-for-endpoint agreement with OpenSTA on post-CTS and post-route designs with
   real SDC files; incremental result identical to a full re-run.
3. **A mutable database and a native format.** Edits, undo, ECO in and out as DEF/Verilog.
   Gate: round-trip through OpenROAD with no differences.
4. **Timing-driven placement plus sizing and buffering.** This is where a new tool can win:
   it is compute-bound, GPU-friendly (DREAMPlace showed 10x and more), and its quality is
   measurable end to end. Gate: on the benchmark set, post-route WNS/TNS and wirelength no
   worse than OpenROAD's `global_placement` + `repair_design` + `detailed_placement`, at a
   fraction of the runtime.
5. **Clock tree synthesis and global routing with layer assignment**, emitting route guides
   that OpenROAD's detailed router accepts. Gate: detailed routing completes with no more DRC
   violations and no worse timing than with OpenROAD's own guides.
6. **Detailed routing, extraction, physical verification.** Only if stages 1 to 5 produced
   something people use. Until then these stay with OpenROAD, Magic and KLayout, as the README
   already says.

Stages 1 to 3 are the cost of entry; stage 4 is the first point where "better than the existing
tool" is a claim that can be tested. A second PDK (for example IHP SG13G2 or GF180MCU, both
open) should be added during stage 2 or 3, because every sky130 assumption that survives until
stage 4 gets expensive.

### 4.4 What should not change

- The verification discipline of AGENTS.md Sections 2 and 7.
- Standard files at every stage boundary. It is the reason each stage can be adopted alone, and
  it keeps the reference tools usable as checkers.
- "Known algorithms, not new ones" until a stage has a measured baseline to beat.

### 4.5 Fit with the rest of the company

This repository exists as a place to try delegated development on public designs, and Grus
Arch is the main line. Stage 1 costs days and is worth doing regardless. Stage 2 is weeks to
months of focused work. Stages 4 and beyond are a product in themselves; starting them is a
company-level decision, not an engineering one, and belongs in the company roadmap rather than
in this file.

## 5. Suggested order of work

1. F1 (honest convergence report), F7 (remove dead CLI options), F8 (document drift): small,
   and they make the status readable.
2. E3.6 speed, then F5 legalizer profile: brings the test suite and the CLI back to "seconds".
3. F9 (test support, CI on the self-hosted runner).
4. Three more designs (`aes`, `ibex`, `jpeg`) through all stages; F2 (map correlation) and the
   E2 picorv32 result fall out of this.
5. F3 and F6 (loud failures in STA and readers).
6. A routed SPEF, then decide E3.4 and E3.5 against it (Section 3).
