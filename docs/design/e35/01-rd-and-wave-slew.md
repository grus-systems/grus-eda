### 1a. The current rule `rd = RD_SCALE x (delay-vs-C slope)` has no good constant

| `RD_SCALE` | Ceff | delay | slew | `_11506_` fall Ceff |
|---|---|---|---|---|
| 2.0 | 0.96 / 8.83% | 0.16 / 7.85% | 0.43 / 8.78% | -8.83% |
| 3.0 | 0.69 / 6.79% | 0.12 / 6.03% | 0.33 / 6.75% | +6.79% |
| 4.5 (shipped) | 0.61 / 17.10% | 0.09 / 15.21% | 0.26 / 17.01% | +17.10% |
| 6.0 | 0.56 / 22.20% | 0.06 / 19.74% | 0.22 / 22.09% | +22.20% |

Ceff is monotone in the scale, but the **zero-error scale differs per arc**: bisecting per row, the shielded arcs
(`ref Ceff / total < 0.93`) need 2.46-3.6 (falls 2.46-2.94, rises 3.07-3.59); unshielded rows do not constrain it.
So no single `RD_SCALE` fits, and the shipped 4.5 is chosen by endpoint arrival (see 1c), not by Ceff.

### 1c. Why 4.5 was shipped: the endpoint arrivals depend on the waveform slew

Routed-SPEF picorv32 endpoint test (`test_picorv32_routed_spef_matches_opensta`, `--ignored`), mismatching fields
(shipped: 136; wns ours -3.233 vs ref -3.148 ns):

| rd rule | waveform slew propagated | mismatches |
|---|---|---|
| 4.5 x delay slope | table slew at Ceff (shipped) | 136 |
| 3.0 x delay slope | table slew at Ceff | 1741 |
| 2.0 x slew slope | table slew at Ceff | 2612 |
| 2.0 x slew slope | 1.00 x table slew at total load | 1066 |
| 2.0 x slew slope | 1.03 x table slew at total load | **16** |
| 2.0 x slew slope | 1.02 / 1.04 / 1.06 x table slew at total load | 155 / 26 / 557 |

An accurate Ceff and delay make the endpoints *worse* until the propagated slew is right: the shipped 4.5
over-estimates Ceff and delay and by that happens to cancel the missing waveform slew.

### 1d. The waveform slew

OpenSTA's driver waveform slew (column 12) vs the table slew (column 11):
- unshielded rows (`ceff/total >= 0.99`, 61 rows): ratio min 0.965, median 0.973, max 1.016 (12 rows above 0.985, mostly high input slew or large load); on average ~3% below the table slew, not understood and not a constant;
- shielded rows: ratio grows with shielding: 1.07-1.13 at `ceff/total` 0.89-0.94, 1.24 at 0.85, 1.46 at 0.725.
  This is close to `table_slew(total) / table_slew(ceff)`.

Candidates against the 76 rows, `k = 2.0`, ours vs OpenSTA waveform slew:
- table slew at Ceff (evaluated at k = 2.0; at the shipped `RD_SCALE` 4.5 it is 2.65% / 19.83%): median 2.69%, max 30.3% (`_11506_` fall);
- table slew at total load (`w1`): median 2.79%, max 11.2%; on shielded rows within -0.4..-3% for rises, -2..-5.6% for falls, one outlier `_06200_` fall -11.2%;
- 0.97 x `w1`: median 0.57%, max 13.9% (better on unshielded rows, worse on shielded);
- a direct simulation of the fitted ramp source behind `rd` into the pi model was tried and is **wrong by 3x**: at large loads
  the fit hits the `dt -> 0` floor (e.g. `_11506_` fall: `rd` 4.24 kohm, Ceff 1.49 pF, step response slew 8.7 ns against a 3.17 ns table slew),
  so the Thevenin ramp model is out of its domain there and its simulated waveform cannot be used.

## 2. Proposal for review

1. **Replace the `rd` rule** in `dmp.rs`/`analysis.rs`: `rd = RD_SLEW_FACTOR x d(table slew)/dC` with `RD_SLEW_FACTOR = 2.0`, delete `RD_SCALE`,
   and correct the doc comment (F4: it describes `ln(0.8/0.2)` but the value is 4.5 and is fitted).
   The constant remains **fitted** (one parameter, flat optimum, measured on 76 rows of one design); the document says so. This closes "Ceff within 2%" only if the
   max 2.38% is accepted as within noise of the criterion, or after one more round of arcs (see 3).
2. **Model the waveform slew** as `table_slew(total_load) x W`, where `W` is a single factor. The measurements give `W = 1.03` as the value that
   makes the routed picorv32 test mismatch count 136 -> 16, but it is not understood (the unshielded rows say 0.97); the proposal is to **not** ship a global
   factor, and to investigate first why the endpoint slew wants +3% while the isolated driver slew wants -3% (candidate: our wire-slew degradation or the
   input-slew handling at the sink, not the driver at all).
3. Collect more `report_dcalc` rows (aes, ibex; fall and rise; loads from 0.3 to 3 pF, several drive strengths) before fixing the constants. 76 rows from one design
   with 6-7 shielded arcs is thin evidence for a constant meant to hold across designs. This is the same instrument as ticket 17.

## 3. Questions for the reviewer

3. Is `table_slew(total)` a defensible first model of the waveform slew, or is there a better closed form (consider that the V1 simulation fails because of the `dt -> 0` floor)?

## 8. Findings after the review: the ramp fit is degenerate almost everywhere, no table scalar explains the residual (2026-11-15)

Instruments: `ramp_fit_degenerate` (dmp.rs; true when even a step through `rd` is slower than the table slew, so `fit_ramp` returns its floor `dt`), the `dt0` column of `test_dmp_rd_rule_sweep`, the capped rules in the same test, and the slope columns of `test_dmp_rd_root_scan`.

- **`dt -> 0` count** (rows whose Ceff solve ends in a degenerate ramp fit, of 7054 picorv32 / 6952 aes): `delay slope x 1/ln2` 3606 / 4078; `x 3` **6986 / 6852 (99%)**; `x 4.5` 7054 / 6945. So with any `rd` that reproduces the Ceff, our model is a **step source behind `rd` with a time offset `t0`**; the saturated-ramp `dt` is unused and the table slew never enters the Ceff solve. The Liberty tables are current-source-like (slew grows more slowly with load than a single-pole RC predicts: slew slope / delay slope is ~1.3-1.5 against 2 for a single pole), so the `rd` that gives the right Ceff is ~3x the single-pole value.
- **Bounding `rd` to keep the fit in the ramp domain does not work**: `min(delay slope x k, table_slew / (ln4 C))` gives Ceff errors up to 56.5% (picorv32) and 15.2% (aes) for every k tested.
- **No cheap table quantity explains the spread of the zero-error `rd`** (281 shielded picorv32 rows with `ceff/total < 0.95`, as in Section 7; the regression ran in a throw-away Python pass over the `ROOT` lines, not in a committed test, log-linear least squares of `rd`): `delay slope` alone leaves a residual of 14% in `rd`; `slew slope` 12%; both 10%; adding input slew, transition, shielding, delay/slew ratio or `rpi * total` changes it by under 1 point. The definition of the slope does not matter either: `rd / slope` has a coefficient of variation of 0.107-0.124 for the local slope at Ceff, the secant Ceff -> total, near cap -> total and 0.5 total -> total (the tables are linearly extrapolated beyond 0.303 pF, so several of these coincide).
- **Conclusion**: with the published method and the tables, a single fitted constant is the best simple rule (about 3 x the delay slope: Ceff median / max 0.70 / 6.79% on picorv32, 0.61 / 2.68% on aes). Deriving the reference's `rd` exactly would need its actual algorithm; OpenSTA's `DmpCeff` source is GPL and off-limits (`AGENTS.md` Section 3b), so that route stays closed.

**Decision proposed** (for the review that follows): (1) stop trying to derive `rd`; E3.5's "done when" is rewritten as a measured error budget instead of an exactness claim; (2) the model change (`RD_SCALE` 3.0 with the propagated driver slew = table slew at the total load) stays held, not because it is wrong but because its gain is concentrated on one extreme-load stage and its cost (picorv32 placed SPEF 0 -> 2 fields, aes placed SPEF 480 -> 524) is not settled; it is re-evaluated when ibex and routed aes can be run; (3) effort moves to the other open items (E1 peak underestimation on jpeg, E2 scale, F3 uncounted skips).

- **The wire model is right for cell-driven nets.** Per-sink wire delay from OpenSTA (sink arrival minus driver arrival, all pins of aes, picorv32, ibex, jpeg) over our Elmore delay: median 1.000 in every Elmore bin (0 to over 1 ns) and every driver-slew bin, p10-p90 about 0.97-1.03 (jpeg's widest spread 0.956-1.044 on the largest Elmore bin). Predicted sink slew `hypot(driver slew, 1.386 x Elmore)` has a mean absolute error of 0.0% (aes, ibex), 0.1% (picorv32), 0.75% (jpeg; 6.3% on nets with Elmore above 10 ps); a factor of 1.7 would improve that by a little but is not needed. So the large SPEF failures on aes/ibex/jpeg do **not** come from wires.
- **Worst paths, stage by stage** (baseline model): each design's worst paths are carried by one or two stages. aes: `_08249_/Y` fall (+0.64 pF, input slew 1.7 ns), our slew 1.326 vs 1.719 ns, then the next mux2 runs 121 ps fast. ibex: `_10092_/Y` fall (0.50 pF, input slew 4-5 ns), our slew 1.68 vs 2.35 ns, then the next stage runs 215 ps fast (ten worst paths); `_21728_` CLK->Q (1.06 pF) slew 5.05 vs 5.21 ns. jpeg: loads of 2.2-7.9 pF and input slews of 5-11 ns (3 to 6 x the 1.5 ns table range) drive errors of 16 ns (`_43767_/Y`: OpenSTA delay 17.65 ns, ours 33.5 ns).
- **Extreme arcs** (`test_dmp_extreme_rows_vs_opensta`, `RD_SCALE` 4.5): where OpenSTA shows no shielding (`ceff/total` 1.0) we are within 2-4%; **where OpenSTA reports strong shielding at a long edge time we do not shield at all**: jpeg `_43767_` A->Y fall (input slew 9.1 ns, total 2.23 pF, Rpi 0.497 kohm, C2 2.12 pF): OpenSTA Ceff 1.196 pF (shield 0.54), delay 17.65 ns, waveform slew 32.0 ns (table slew 10.5); ours Ceff 2.185 pF, delay 31.8 ns (+80%); B->Y fall: Ceff +125%. No `rd` reproduces that Ceff (the zero-error `rd` search hits its lower bound), and clamping the slope's input slew to the table range makes no difference. Physically a 1 ns RC (Rpi x C2) cannot shield a 10-30 ns edge, so this looks like an implementation-specific behaviour of the reference at extreme loads and slews, not something the published method gives. ibex `_10092_` fall (input slew 4-5 ns, shield 0.96): Ceff +2.5 to +3.1%, but the waveform slew is 2.34 against a table slew of 1.66 ns (x1.41).
- **Port-driven nets are a separate small question**: ibex `rst_ni` (1664 sinks, ideal port, no `set_input_transition`): OpenSTA wire delay is exactly `ln 2 x Elmore` (ratio 1.4427), our slew degrade matches; that one net costs 0.80 ns on all 1655 RESET_B endpoints. aes `ld` and jpeg `rst` (ports with `set_input_transition 0.15`) have a reference delay of about 0.45 and 0.40 of the (1.386-based) Elmore; applying `ln 2 x Elmore` to ports, or the single-pole ramp delay to all nets, helps ibex (placed SPEF mismatching fields 8855 -> 2199) but hurts aes (480 -> 704-849), jpeg (6147 -> 8396-8504) and picorv32 (0 -> 3), so no rule was adopted (the experiments were reverted). Needs per-sink data on port nets (the pin dump has no port arrival; derive it from the SDC input delay).
- **What this changes**: the DMP question is now narrow and well located: (a) the waveform slew of fall arcs with long input slews (above the 1.5 ns table range), where the reference is 30-40% above the table slew even at mild shielding; (b) extreme loads (above ~1 pF, 3x the table range and more) with long edges, where the reference shields and we do not. The residuals in the table-range regime are small (Ceff within about 3-7%), and the wire model is not involved.

(Here `half_pred = 0.5 * (hypot(s_in, ln(4) * Elmore) - s_in)` and `degrade = sqrt(max(0, s_out^2 - s_in^2))`.)

Findings:
- **Exact port-driven wire rule across all 4 designs (both `tin = 0` and `tin = 0.150 ns`)**: OpenSTA computes primary-input port-driven wire delay as `dly = ln(2) * Elmore` (median `dly / (ln2 * elmore) = 1.0000` on every design, including `aes ld` `0.6931`, `ibex rst_ni` `0.6931`, `jpeg ena` `0.6931`, `jpeg rst` `0.6931`) and adds wire slew **linearly**, `s_out = s_in + 2 * dly = s_in + ln(4) * Elmore` (`max |dly - (s_out - s_in)/2| <= 1.17e-6 ns`, at the `collect_pins.sh` 6-decimal formatting floor).
- **Correction to Section 9**: Section 9 noted `0.45` and `0.40` of Elmore on `aes ld` and `jpeg rst` because that earlier check inferred Elmore from `degrade = sqrt(s_out^2 - s_in^2) / 1.386` (assuming quadratic slew addition) rather than direct Elmore. Because OpenSTA adds slew linearly on port nets, `degrade / elmore` inflates when `s_in > 0` (`tin = 0.150 ns`), explaining both the `0.40..0.45` illusion on `aes ld` / `jpeg rst` and why the earlier experiment of changing `dly` alone without changing port sink slew from quadratic to linear hurt `aes` and `jpeg`. Both rules belong together exclusively on primary-input port-driven nets (`pin_cells[drv].is_none()`), leaving cell-driven nets unchanged (`dly = Elmore`, `s_out = hypot(s_in, ln(4) * Elmore)`).
