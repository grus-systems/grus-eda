Status: **Sections 1-3 are SUPERSEDED by Section 5 (the slew-slope rule was overfit to 7 arcs and is withdrawn); read Section 5 first.** Originally: proposal, measured on a probe, not implemented. Probe patch: `probe.patch` (this folder; apply on

measurement test and to `solve_dmp`; it is a measurement tool, not a candidate change). Every number below was
produced on 2026-11-15 on the M4 Mac mini with the committed `dcalc_routed_ref.txt` (76 rows) and a

## 1. What was measured

Test `test_dmp_matches_opensta_report_dcalc_routed` (76 `report_dcalc` rows, routed SPEF; pi model already exact),
ours vs OpenSTA, median / max |error|.

### 1a. The current rule `rd = RD_SCALE x (delay-vs-C slope)` has no good constant

| `RD_SCALE` | Ceff | delay | slew | `_11506_` fall Ceff |
|---|---|---|---|---|
| 2.0 | 0.96 / 8.83% | 0.16 / 7.85% | 0.43 / 8.78% | -8.83% |
| 3.0 | 0.69 / 6.79% | 0.12 / 6.03% | 0.33 / 6.75% | +6.79% |
| 4.5 (shipped) | 0.61 / 17.10% | 0.09 / 15.21% | 0.26 / 17.01% | +17.10% |
| 6.0 | 0.56 / 22.20% | 0.06 / 19.74% | 0.22 / 22.09% | +22.20% |

Ceff is monotone in the scale, but the **zero-error scale differs per arc**: bisecting per row, the shielded arcs
(`ref Ceff / total < 0.93`) need 2.46-3.6 (falls 2.46-2.94, rises 3.07-3.59); unshielded rows do not constrain it.
So no single `RD_SCALE` fits, and the shipped 4.5 is chosen by endpoint arrival (see 1c), not by Ceff.

### 1b. The zero-error `rd` tracks the table's *slew* slope, not its delay slope

For the 7 shielded rows (rd at the zero-error scale, slopes taken at the reference Ceff):

| arc | `rd_root / delay_slope` | `rd_root / slew_slope` |
|---|---|---|
| `_06058_` B->Y fall / rise | 2.90 / 3.22 | 2.13 / 2.23 |
| `_11506_` Q rise / fall | 3.07 / 2.46 | 2.14 / 1.91 |
| `_09979_` Q fall | 2.57 | 1.99 |
| `_04923_` A->Y fall | 2.81 | 2.13 |
| `_06198_` C->X fall | 2.94 | 2.22 |

The delay-slope ratio is 2.46-3.22 and splits by transition; the slew-slope ratio is 1.91-2.23 and does not.

`rd = k x (slew slope)` with `k` fixed, same 76 rows:

| k | Ceff | delay | slew |
|---|---|---|---|
| 1.6 | 0.79 / 7.33% | 0.17 / 6.52% | 0.46 / 7.29% |
| 1.8 | 0.83 / 2.74% | 0.16 / 2.09% | - |
| 1.9 | 0.80 / 2.55% | 0.15 / 1.74% | - |
| **2.0** | **0.74 / 2.38%** | **0.15 / 1.57%** | **0.44 / 1.74%** |
| 2.1 | 0.62 / 3.47% | 0.14 / 3.09% | - |
| 2.2 | 0.64 / 5.04% | 0.13 / 4.48% | - |
| 2.4 | 0.73 / 7.78% | 0.13 / 6.92% | 0.39 / 7.74% |

At k = 2.0 the worst Ceff error falls from 17.10% to 2.38% (the E3.5 done criterion is 2%), the worst delay error
from 15.21% to 1.57%, with one dimensionless constant and a flat optimum (k 1.8-2.0 within 0.4 points). `k` is
still fitted. Why about 2 is not derived; candidate readings (for example a ratio between the 20-80 slew and the
50% delay response of the Thevenin ramp model) are not tested.

### 1c. Why 4.5 was shipped: the endpoint arrivals depend on the waveform slew

Routed-SPEF picorv32 endpoint test (`test_picorv32_routed_spef_matches_opensta`, `--ignored`), mismatching fields
(shipped: 136; wns ours -3.233 vs ref -3.148 ns):

| rd rule | waveform slew propagated | mismatches |
|---|---|---|
| 4.5 x delay slope | table slew at Ceff (shipped) | 136 |
| 3.0 x delay slope | table slew at Ceff | 1741 |
| 2.0 x slew slope | table slew at Ceff | 2612 |
| 2.0 x slew slope | 1.00 x table slew at total load | 1066 |
| 2.0 x slew slope | 1.03 x table slew at total load | **16** |
| 2.0 x slew slope | 1.02 / 1.04 / 1.06 x table slew at total load | 155 / 26 / 557 |

An accurate Ceff and delay make the endpoints *worse* until the propagated slew is right: the shipped 4.5
over-estimates Ceff and delay and by that happens to cancel the missing waveform slew.

### 1d. The waveform slew

OpenSTA's driver waveform slew (column 12) vs the table slew (column 11):
- unshielded rows (`ceff/total >= 0.99`): ratio 0.965-0.985 (a constant ~3% below the table slew, not understood: possibly a threshold convention);
- shielded rows: ratio grows with shielding: 1.07-1.13 at `ceff/total` 0.89-0.94, 1.24 at 0.85, 1.46 at 0.725.
  This is close to `table_slew(total) / table_slew(ceff)`.

Candidates against the 76 rows, `k = 2.0`, ours vs OpenSTA waveform slew:
- table slew at Ceff (shipped): median 2.69%, max 30.3% (`_11506_` fall);
- table slew at total load (`w1`): median 2.79%, max 11.2%; on shielded rows within -0.4..-3% for rises, -2..-5.6% for falls, one outlier `_06200_` fall -11.2%;
- 0.97 x `w1`: median 0.57%, max 13.9% (better on unshielded rows, worse on shielded);
- a direct simulation of the fitted ramp source behind `rd` into the pi model was tried and is **wrong by 3x**: at large loads
  the fit hits the `dt -> 0` floor (e.g. `_11506_` fall: `rd` 4.24 kohm, Ceff 1.49 pF, step response slew 8.7 ns against a 3.17 ns table slew),
  so the Thevenin ramp model is out of its domain there and its simulated waveform cannot be used.

## 2. Proposal for review

1. **Replace the `rd` rule** in `dmp.rs`/`analysis.rs`: `rd = RD_SLEW_FACTOR x d(table slew)/dC` with `RD_SLEW_FACTOR = 2.0`, delete `RD_SCALE`,
   and correct the doc comment (F4: it describes `ln(0.8/0.2)` but the value is 4.5 and is fitted).
   The constant remains **fitted** (one parameter, flat optimum, measured on 76 rows of one design); the document says so. This closes "Ceff within 2%" only if the
   max 2.38% is accepted as within noise of the criterion, or after one more round of arcs (see 3).
2. **Model the waveform slew** as `table_slew(total_load) x W`, where `W` is a single factor. The measurements give `W = 1.03` as the value that
   makes the routed picorv32 test mismatch count 136 -> 16, but it is not understood (the unshielded rows say 0.97); the proposal is to **not** ship a global
   factor, and to investigate first why the endpoint slew wants +3% while the isolated driver slew wants -3% (candidate: our wire-slew degradation or the
   input-slew handling at the sink, not the driver at all).
3. Collect more `report_dcalc` rows (aes, ibex; fall and rise; loads from 0.3 to 3 pF, several drive strengths) before fixing the constants. 76 rows from one design
   with 6-7 shielded arcs is thin evidence for a constant meant to hold across designs. This is the same instrument as ticket 17.

## 3. Questions for the reviewer

1. Is basing `rd` on the slew slope defensible from the DMP paper (Dartu, Menezes, Pileggi 1996), or is this curve-fitting to 7 arcs? What would a derivation look like?
2. Is shipping step 1 alone acceptable while step 2 is open, given that it makes the picorv32 routed endpoint comparison worse (136 -> 2612 mismatches) because the shipped
   constant currently compensates for the missing waveform slew? Or should 1 and 2 land together?
3. Is `table_slew(total)` a defensible first model of the waveform slew, or is there a better closed form (consider that the V1 simulation fails because of the `dt -> 0` floor)?
4. What would you collect next to separate "fitted constant" from "structural error"?

## 4. Review and disposition (2026-11-15)

external reviewer was unavailable (the review tool failed; not investigated further). The review was run with a second external reviewer instead. The full review text is not included in this repository. Verdict: **agree with changes**. All seven findings are accepted:

- S2 slew-slope rule is an empirical hypothesis, not a derivation (7 shielded arcs). Stated as such; the ideal single-pole RC reference (delay-50% slope `ln2 R`, 20-80 slew slope `ln4 R`) is the baseline any derivation must explain the measured 1.9-2.2 ratio against.
- S2 Ceff max 2.38% does not meet the 2% criterion. E3.5 is **not** closed; the "accept as noise" wording in Section 2.1 is withdrawn.
- S2 the 1.03 waveform-slew factor was chosen on the same endpoint set it improves (it may compensate path-level error). Recorded as an exploration result only, no factor is fixed; `table_slew(total)` is a provisional baseline.
- S2 steps 1 and 2 are one acceptance unit; the `rd` replacement is held back (it raises endpoint mismatches 136 -> 2612 alone).
- S2 next measurement: same cell and transition with only the load varied, rise/fall, several input slews and shielding degrees; separate the data used to choose constants from independent evaluation data (for example fit on picorv32, evaluate on gcd/aes/ibex).
- S3 per-arc error tables and the endpoint field breakdown are missing from this document; the committed probe patch regenerates them, and the next round records them in `docs/results.md`.

**Decision**: no model change is made. The next unit is the data collection above (a `report_dcalc` collection script committed with its output, on gcd and aes/ibex for the independent set, plus a load-sweep series on picorv32 cells), which needs the Docker/OpenSTA instrument.

## 5. Update: the broad collection overturns the slew-slope rule (2026-11-15, later the same day)

New instrument: `tests/designs/collect_dcalc.sh` (committed; runs OpenSTA `report_dcalc` over every (input, output) pin pair of a design in the pinned image, infers the arc sense from the printed transitions, skips mixed-sense pairs) and the data it wrote: `tests/designs/picorv32/dcalc_routed_all.txt` (7054 rows; stride 6 plus every pair on a net with >= 6 pins; 4300 pairs kept of 19783) and `tests/designs/gcd/dcalc_routed_all.txt` (1138 rows, all pairs). Rust side: `solve_dmp_with` (the `rd` rule as a parameter; `solve_dmp` is unchanged in behaviour), `test_dmp_rd_rule_sweep` and `test_dmp_rd_root_scan` in `analysis.rs`.

- **gcd has no shielded rows** (OpenSTA Ceff >= 97% of total on all 1138), so it is not an independent test of shielding; it only shows the unshielded rows stay within ~2% under any rule. The independent evaluation set must come from designs with shielded nets (aes, ibex).
- **`rd = 2.0 x slew slope` does not generalise**: on the 7054 picorv32 rows its worst Ceff error is 8.83% (the 76-row 2.38% was an artifact of which arcs were collected). Worst rows are falls with very large input slew (1.4-2.5 ns) and mild shielding, where it over-shields.
- **The zero-error `rd` on the 280 well-conditioned shielded rows** (shield < 0.95; weaker shielding makes the root ill-determined) is `3.01 x delay slope` (p10-p90 2.61-3.34, cv 12%) versus `2.29 x slew slope` (cv 16%). So the **delay-slope rule is the better-centred one and the Ceff-consistent constant is ~3, not 4.5**; this agrees with the earlier note in `docs/e3-sta.md` ("one value fits arrival (4.5-5) but not Ceff (about 3)"). Rises 3.28, falls 2.92; input slew above 1.5 ns (7 rows) departs (1.6). The k = 2 slew-slope proposal is withdrawn.
- **Endpoints, routed picorv32 (`RD_SCALE` 3.0 with the propagated slew = table slew at the *total* load, no fudge factor)**: 53 mismatching fields against 136 shipped. The factor on that slew: 1.00 -> 53, 1.01 -> 11, 1.02 -> 6, 1.03 -> 12 (a residual ~2% that is not understood and is not applied). Placed picorv32: 2 mismatches (baseline 0; the picorv32 SPEF test would fail on its 2% TNS tolerance: TNS -89.25 vs -91.62, WNS -1.679 vs -1.715). `RD_SCALE` 3.5 with 1.0: 64; with 1.03: 128. gcd placed/routed unaffected. aes/ibex/jpeg could not be run (artifacts not generated here).
- **Current recommendation (to be reviewed, then implemented as one change)**: `RD_SCALE = 3.0` (a measured, Ceff-consistent constant with its spread documented, still fitted, not derived) **and** the propagated driver slew = table slew at the total load, with the F4 doc-comment fix. Both land together. Before that: generate aes and ibex inputs, collect their `report_dcalc` tables (independent evaluation set; the constant is fitted on picorv32 only), and re-run all ignored wire tests under the candidate.
